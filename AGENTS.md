# AGENTS.md — правила работы

Правила для ассистента и участников при работе с проектом.

## Контуры работы

Проект используется в двух контурах:

### Контур сбора и постановки требований (база знаний)
- Назначение: сбор, извлечение и постановка требований.
- Работает с `RAW/`, `database/`, `.project-context/active/requirements/`, `playbooks/`.
- Поток: `RAW → database → .project-context/active/requirements`.
- Требования не выдумываются — только извлекаются из источников.
- **Разделение баз знаний**: материалы о регламенте проведения хакатона (правила, инструкции, критерии оценки) → `hackathon_database/`; требования к самой системе → `database/`.

### Контур разработки (документация по коду)
- Назначение: разработка и документация программного кода.
- Работает с кодом проекта и использует базу знаний как источник требований и контекста.
- **Может пополнять базу знаний**: разработчик может принести новые требования в проект.
- Новые требования из контура разработки фиксируются через `playbooks/process_source.md` и `playbooks/manage_requirements.md` (как новые источники/чанки/требования), а не вносятся напрямую в спецификацию без обработки.

## Начало работы (обязательно)
- **Первый раз в сессии прочитай `START_HERE.md`** — порядок работы и точки входа (если файл ещё не был прочитан).
- Затем прочитай `.project-context/active/sources/SOURCE-20260923-124.md` (состояние проекта) и `.project-context/active/sources/SOURCE-20260923-717.md` (маршруты чтения по задаче).

## Категории информации
Отделяй в документах четыре категории:
- **Факт** — подтвержденное данными; обязан иметь источник.
- **Предположение** — гипотеза, не подтвержденная данными.
- **Вопрос** — открытый пункт, требующий уточнения.
- **Согласованное решение** — утвержденное участниками.

## Обработка файлов
- Если не ясно, что нужно сделать с файлом исходя из промпта, **обязан уточнить правила обработки файла**, а не придумывать процесс сам.
- Язык исходников, загружаемых в проект, — **русский**.

## Неоднозначные фрагменты
- Неоднозначные фрагменты помечай как **открытые вопросы** (`Q-NNN`).
- Недосказанность — это открытый вопрос, не выдумывай отсебятину.
- Открытый вопрос задай в том промпте, в котором он возник; больше не повторяй, если он остался неотвеченным.
- Список открытых вопросов выдавай **по требованию**, не всякий раз.

## Уточнение требований новым источником
- Новый источник должен **уточнять** предыдущие требования.
- Если новый источник **радикально меняет** предыдущее требование — это открытый вопрос, который следует задать, чтобы разрешить конфликт.

## Источники
- У каждого факта должен быть источник (ссылка на файл в `RAW/` или `database/`).
- Обязан ссылаться на каждый источник при использовании факта.

## Утвержденные требования
- Новое обсуждение не отменяет утвержденное требование автоматически.
- Изменение требования требует явного согласования.

## Сохранность данных
- Оригиналы сохраняй, существующие изменения не затирай.
- Удалять файлы из проекта запрещено.
- При подготовке новой ревизии требований сохраняй предыдущую редакцию отдельным неизменяемым снимком (например `current_specification-v2.md`), а `current_specification.md` всегда содержит актуальные требования.

## Процедуры
- Подробные процедуры вынесены в `playbooks/`.
- Открывай только нужные playbooks, не загружай все сразу.

## Расположение материалов в публичной версии

Каталоги `database/`, `hackathon_database/`, текстовые источники `RAW/` и документы `COOKED/` объединены с `.project-context/active/`. Перед обращением к историческому пути используйте [указатель материалов](.project-context/SOURCE_MAP.md). Исторические копии документов в контексте могут описывать прежнюю структуру. Новые знания записывайте в контекст; проверяйте утверждения по актуальному коду и тестам.

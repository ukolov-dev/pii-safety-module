# Отчёт об улучшении production v3.13

Дата прогона: 2026-09-23.

## Решение о продвижении

После пяти независимых циклов в production продвинут кандидат **v3.13**. Каждый
цикл использовал новый sealed holdout, который разработчики кандидата не читали.
Критерий продвижения: минимум +10 процентных пунктов F1, precision не ниже
baseline, round-trip 100% и сохранение SLA.

| Метрика на sealed holdout v10 | v3.3 baseline | production v3.13 | Изменение |
|---|---:|---:|---:|
| Precision | 70,53% | 82,80% | +12,27 п.п. |
| Recall | 65,69% | 75,49% | +9,80 п.п. |
| F1 | 68,02% | 78,97% | **+10,95 п.п.** |
| Exact mask | 64/110 | 81/110 | +17 случаев |
| Exact round-trip | 110/110 | 110/110 | без изменений |

Первоначальный v3.13 без unit-регрессии показывал 80,81% F1. После исправления
переноса контекста даты между предложениями итоговый честный результат — 78,97%;
он всё равно превышает установленный порог 78,02%.

## Что изменено

- обнаружение кандидатов отделено от privacy/utility-решения `should_mask`;
- расширены ownership-aware правила для ФИО, адресов и документов;
- добавлены контекстные suppressions для публичных, организационных, учебных и
  технических значений;
- сохранены checksum/валидация для структурированных реквизитов;
- добавлен clause boundary для дат, исключающий перенос `дата рождения` на
  следующее предложение;
- для payload от 100 000 символов без сложных семантических маркеров включён
  безопасный быстрый путь через v3.3.

## Исследовательский материал

Изучен гибридный подход `redmadrobot-rnd/pii-guard`: rules/checksum для
структурированных реквизитов и локальный ruBERT для PERSON/address. Модель
`rubert-base-pii-ner` не включена в production: около 700 МБ FP32-весов и тяжёлые
runtime-зависимости требуют отдельного CPU/GPU/quantization benchmark и схемы
горизонтального масштабирования. Сохранён model-ready эксперимент v3.14, но
production остаётся локальным лёгким rule pipeline.

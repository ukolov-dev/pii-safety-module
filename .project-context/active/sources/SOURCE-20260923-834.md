### Автоматические проверки

Обязательны обе проверки: проверка качества кода и нагрузочное тестирование. Решение, не прошедшее проверку качества кода или не развёрнутое для нагрузочного тестирования, не будет учтено.

#### Проверка качества кода

Проверка запускается автоматически после загрузки решения на платформу. Принимается только один архив в формате ZIP с исходным кодом в корне или в понятной структуре каталогов.

Требования к архиву:

- Включать только исходный код решения.
- Не включать объёмные файлы: датасеты, дампы, архивы, медиа и скомпилированные бинарники.
- Не включать каталоги зависимостей: `node_modules`, `.venv`, `venv`, `env`.
- Не включать каталоги сборки: `target`, `build`, `dist`, `out`, `bin`, `obj`.
- Не включать служебные каталоги и файлы: `.git`, `.idea`, `__pycache__`, `.coverage`.
- Размер архива должен быть разумным.

#### Нагрузочное тестирование

Участник должен развернуть решение, реализующее контракт API с эндпоинтом `POST /process`, и обеспечить его доступность по указанному URL на время прогона.

Проверяющая система подаёт нагрузку по эталонному датасету и оценивает точность маскирования, точность демаскирования и поведение под нагрузкой.

Контракт API приведён в Приложении A к заданию, инструкция по прохождению проверки — в Приложении B.

## ТЗ на систему

### Назначение

Разработать модуль защиты персональных данных, встраиваемый в цепочку взаимодействия «система-потребитель — LLM».

Модуль должен снижать риск утечки персональных данных при росте числа обращений к LLM, обеспечивать соответствие требованиям законодательства РФ и ЦБ и заменять разрозненные решения единым стандартом безопасности.

### Основные требования

1. **Функционал:** идентификация → маскирование → демаскирование персональных данных.
2. **Качество:** точность обработки не менее 95%.
3. **Интеграция:** возможность легко встраивать модуль в цепочку взаимодействия системы-потребителя с LLM.
4. **Поддержка нескольких систем-потребителей** с индивидуальными настройками.
5. **Логирование.**
6. **Обработка контекста:** поддержка массивов до 100 000 токенов.
7. **Производительность:** задержка ответа (Latency) не более 1 секунды, целевой RPS не менее 1000.
8. **API для проверки:** реализация эндпоинта `POST /process` согласно контракту API.

### Типы персональных данных

Обязательно покрытие всех перечисленных типов:

1. ФИО.
2. Дата рождения.
3. Место рождения.
4. Серия и номер паспорта.
5. Гражданство.
6. Орган, выдавший паспорт.
7. Код подразделения.
8. Дата выдачи паспорта.
9. Серия и номер водительского удостоверения.
10. Адрес, в том числе отдельно: страна, индекс, город, улица, дом, квартира.
11. Email.
12. Номер телефона.
13. ИНН.
14. Номер платёжной банковской карты.
15. CVV-код.
16. ПИН-код карты.
17. Имя держателя карты.

### Надёжность и безопасность

- Качество обработки, отказоустойчивость и масштабируемость.
- Выполнение SLA по скорости ответа, доступности и стабильности.
- Недопустимость критичных ошибок и соблюдение требуемого уровня качества обработки.
- Соблюдение требований безопасности и приватности: отсутствие утечек, шифрование и минимизация данных.

### Дополнительные требования

1. Токенизация и детокенизация либо замена персональных данных синтетическими.
2. Гибкая настройка вида маскирования или токенизации в зависимости от системы-потребителя.
3. Возможность выдерживать RPS 2000 при задержке ответа не более 1 секунды.
4. Идентификация документов, удостоверяющих личность, кроме паспорта РФ.
5. Маскирование только при наличии нескольких однозначно идентифицированных типов персональных данных. Например: ПИН-код карты отдельно не маскируется; ПИН-код вместе с номером карты маскируется.
6. Возможность изменения этих настроек.

# Управление требованиями

Процедура ведения спецификации требований в `COOKED/requirements/`.

## Спецификация
- Спецификация одна: `COOKED/requirements/current_specification.md`, и она всегда содержит актуальные требования.
- Перед изменением сохраняй предыдущую редакцию отдельным неизменяемым снимком (например `current_specification-v2.md`), текущую не затирай.
- Неподтвержденные предложения не выдавай за согласованные требования.

## Карточка требования
Каждое требование описывается карточкой со следующими полями:
- **REQ-ID** — идентификатор требования (`REQ-001`, по `database/working/id_rules.md`).
- **потребность** — какую потребность закрывает.
- **роль** — для какой роли/пользователя.
- **сценарий** — сценарий использования.
- **поведение** — ожидаемое поведение системы.
- **ограничения** — ограничения и допущения.
- **источник** — ссылка на источник (`SRC-NNN` и/или чанк `CH-SRC-NNN-NN`).
- **статус согласования** — `предложено | согласовано | отклонено`.
- **проверяемые критерии** — `AC-ID` (критерии приемки, `AC-001`).

## Формат карточки
```yaml
REQ-001:
  потребность: <какую потребность закрывает>
  роль: <для какой роли>
  сценарий: <сценарий использования>
  поведение: <ожидаемое поведение>
  ограничения: <ограничения и допущения>
  источник: <SRC-NNN / CH-SRC-NNN-NN>
  статус_согласования: предложено
  критерии_приемки:
    - AC-ID: <AC-001>
      описание: <проверяемый критерий>
```

## Порядок работы
1. Извлеки требование из чанка/источника.
2. Проверь занятые ID в спецификации; выдай следующий номер `REQ-`.
3. Создай карточку в спецификации.
4. Согласуй с участниками; обнови статус согласования.
5. При изменении — сохрани предыдущую редакцию неизменяемым снимком, обнови `current_specification.md`.
6. После значимых изменений обновляй `database/current_context.md`.
